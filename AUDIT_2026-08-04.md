# Lead-Scraper Security & Code Audit

**Scope:** `/Users/paulmadut/Desktop/Projects/Lead-Scraper/frontend`
**Date:** 2026-08-04

---

## 1. Executive Summary

The app cannot currently be built at all (`pnpm build` exits 1), and its paid-token economy has no gate on it: any user who signs in with a Google account can mint themselves unlimited tokens with a single `fetch` call. Because the token balance is the *only* thing standing between a user and unbounded Google Places API calls billed to your Google Cloud account, that single endpoint is simultaneously a total monetization bypass and an uncapped spend hole on your card. Secondary but serious: when the Places API fails for any reason, the error is swallowed and returned as "success with 0 results" while still charging the user 5 tokens, so quota exhaustion silently drains balances and produces no error anywhere except the server console.

**Fix before scraping a single real lead:** delete or authorization-gate `POST /api/tokens/add` (`src/app/api/tokens/add/route.ts:32`). Everything else can wait a day; that one cannot.

**Verification status:** Sections marked **[VERIFIED]** were adversarially re-checked against the code (and in some cases reproduced). Sections marked **[UNVERIFIED]** were found by static review but not independently confirmed; treat their severity as an estimate.

## 2. Critical

### C1. Any authenticated user can grant themselves unlimited tokens **[VERIFIED]**
**`src/app/api/tokens/add/route.ts:24,32`**

The POST handler does exactly three things: checks for a Bearer header, calls `adminAuth.verifyIdToken(idToken)`, and validates that `body.amount` is a number `> 0`. There is no admin custom-claim check (`decodedToken` is used only for `.uid`), no payment/webhook/order verification, no server-side package lookup, no upper bound, no integer check, no idempotency key, and no rate limit. `AdminTokenService.addTokens` (`src/services/adminTokenService.ts:86-120`) then unconditionally increments `tokens/{uid}.balance` via the Admin SDK, bypassing Firestore rules entirely.

*Note on wording:* the endpoint **is** authenticated (forged/expired tokens are rejected). The defect is missing **authorization**. Since sign-up is open Google OAuth (`src/components/AuthProvider.tsx:106`), that distinction does not reduce exploitability at all.

**Failure scenario:** A user opens devtools and runs
```js
fetch('/api/tokens/add', {method:'POST',
  headers:{Authorization:`Bearer ${idToken}`,'Content-Type':'application/json'},
  body:JSON.stringify({amount:1000000})})
```
Response is `200` with `newBalance: 1000000`. They now scrape indefinitely on your `GOOGLE_MAPS_API_KEY`. `src/app/api/search/route.ts:99,162` gates billable Places calls *solely* on token balance, with no per-user rate limit or daily cap.

**Confirmed absent as mitigations:** no `middleware.ts` anywhere in the project; `vercel.json` only rewrites `/__/auth/*`; `nginx.conf` proxies `/` wholesale with no deny rules; no `NODE_ENV` guard; no Stripe/Paddle/any payment dependency in `package.json` or `src/`. Grep finds **zero** callers of `/api/tokens/add` in `src/`, so this is a bare mint endpoint, almost certainly a dev leftover that shipped.

**Fix:** Delete the route. If admin top-ups are needed later, require `decodedToken.admin === true` plus a server-verified order ID with an idempotency key, and derive the amount from a server-side SKU in `PRICING_CONFIG.TOKEN_PACKAGES` rather than the request body. When you wire payments, credits must originate only from a signature-verified Stripe webhook keyed on the Stripe event ID.

### C2. Build is completely broken: `output: 'export'` conflicts with dynamic routes and API handlers **[VERIFIED, reproduced]**
**`next.config.ts:3`**

`output: 'export'` (static export) coexists with a dynamic route `src/app/dashboard/leads/[id]/page.tsx` that has no `generateStaticParams()` (grep finds none anywhere, nor any `force-static`), plus four server route handlers (`api/search`, `api/tokens/balance`, `api/tokens/add`, `api/test-admin`) that depend on `firebase-admin` and server-only env vars.

**Failure scenario:** `pnpm build` fails at "Collecting page data" with exit code 1: `[Error: Page "/dashboard/leads/[id]" is missing "generateStaticParams()" so it cannot be used with "output: export" config.]` The app cannot be built or deployed in its current state. Even if `generateStaticParams` were added, the API routes would be dead code with no server to run them, silently breaking search and token operations.

**Fix:** Remove `output: 'export'` (and `trailingSlash` / `images.unoptimized` if no longer needed) and deploy to a Node/serverless target. The app needs a server for `firebase-admin`. Do not keep both architectures.

## 3. High

### H1. Users are charged 5 tokens when the Places API fails; all errors swallowed **[VERIFIED]**
**`src/services/googlePlaces.ts:106-109, 133-136, 166-169, 193-196`** → **`src/app/api/search/route.ts:152-162`**
*(Downgraded from critical: real billing-integrity bug, but not a security hole, bounded at 5 tokens per user-initiated attempt, and refundable.)*

`GooglePlacesService` never throws. Both `searchNearbyBusinesses` and `searchBusinessesByText` catch everything and return `[]`, and any non-OK Places status (`OVER_QUERY_LIMIT`, `REQUEST_DENIED`, `INVALID_REQUEST`, expired key, network failure) just `console.error`s and breaks. `BusinessLeadService.searchBusinesses` adds no error handling on any of its three paths, so the catch block at `route.ts:144-150` is unreachable for API failures. Execution falls through to billing, where `actualCost = Math.max(1 + 0*1, MIN_CHARGE=5) = 5`.

**Failure scenario:** Your key hits its daily quota. Every search from then on returns `success: true, businesses: []` and charges 5 tokens. Users retry, draining their balances for nothing, with no error surfaced anywhere but the server console and no refund logic.

**Fix:** Throw a typed `PlacesApiError` (carrying the Google status) for any status other than `OK`/`ZERO_RESULTS`; remove the catch-and-return-`[]` blocks. The existing `searchError` catch in the route will then return 500 without charging. Treat `ZERO_RESULTS` as a legitimate empty result and decide explicitly whether it should incur `MIN_CHARGE`.

### H2. Token doc auto-created with 200 free tokens on every read; delete-and-recreate = infinite credits **[UNVERIFIED]**
**`src/services/adminTokenService.ts:27,49,51`**

`getTokenBalance()` and the deduct pre-flight path seed `tokens/{uid}` with `balance: 200` whenever the doc does not exist. The grant is keyed only on document existence, with no `initialGrantApplied` flag. No `firestore.rules` file exists anywhere in the repo, and `query.ts` writes to Firestore with the client SDK, so rules strictness is unknown. If rules are in default/test mode, a user deletes their own `tokens/{uid}` doc from the browser and the next balance read re-seeds 200 tokens, repeatable indefinitely.

**Fix:** Commit a `firestore.rules` that denies all client read/write on `tokens` (Admin SDK only). Track the grant idempotently in a separate record that survives balance-doc deletion.

### H3. IDOR: search results readable by ID with no ownership check **[UNVERIFIED]**
**`src/services/query.ts` (`getSearchResultsById`) and `src/app/dashboard/leads/[id]/page.tsx`**

Both read `searchQueries/{id}` with the client SDK and return/render the whole document (including `userId` and every scraped lead) without comparing `data.userId` to the signed-in uid. Access control rests entirely on unmanaged, uncommitted Firestore rules. The detail page also duplicates the already-existing (and otherwise unused) `getSearchResultsById`.

**Fix:** Commit rules enforcing `request.auth.uid == resource.data.userId` for reads on `searchQueries`, add a client-side `userId` check for UX, and ideally move the read behind an authenticated API route that checks `decodedToken.uid === doc.userId`.

### H4. Client owns persistence of paid search results **[UNVERIFIED]**
**`src/services/query.ts` (`saveSearchQuery`), called from `src/app/dashboard/search/Search.tsx:137`**

The server scrapes and charges, but the *client* writes the results doc via `addDoc` on `searchQueries`. `userId`, `resultCount`, and `results` are all client-writable, and one logical transaction (scrape → charge → save) is split across two trust domains.

**Fix:** After `deductTokens` succeeds in `api/search/route.ts`, write the `searchQueries` doc with `adminDb` in the same request. Delete `saveSearchQuery` from the client.

### H5. Search results silently lost if the Firestore save fails **[UNVERIFIED]**
**`src/app/dashboard/search/Search.tsx` (`saveSearchQuery` at :137, then unconditional `router.push('/dashboard')`)**

The `saveSearchQuery` call is wrapped in a try/catch that only logs. The redirect happens regardless, and `/dashboard` re-fetches the latest search from Firestore, so on a save failure the user loses results they were just charged for.

**Fix:** Render results on the search page instead of redirecting, or make the redirect conditional on the save succeeding with a retry UI. Never discard paid-for in-memory results.

### H6. Token charge decoupled from the scrape, with no compensation path **[UNVERIFIED]**
**`src/app/api/search/route.ts:99` (pre-flight) → scrape → `:162` (deduct)**

Check-then-act around an expensive operation. Two concurrent searches both pass the same balance snapshot; both incur the full Google bill; the second `deductTokens` throws "Insufficient tokens" inside its transaction and the route returns 500 after the spend was already made and results were in hand. The user gets nothing and retries, doubling cost. No idempotency key, so client retries double-charge.

**Fix:** Reserve `estimatedCost` transactionally *before* calling Google, then refund `estimated - actual` in a second transaction. On scrape failure, refund the reservation. Add a per-user in-flight guard or idempotency key.

### H7. Sequential N+1 Place Details calls will time out and overbill **[UNVERIFIED]**
**`src/services/googlePlaces.ts:127,175,187`**

`getBusinessDetails` is awaited one at a time inside the result loop, plus a hardcoded 2000ms sleep per pagination token. A `max_results=100` search issues 1 geocode + up to 5 search pages + ~100 sequential Details calls + ~10s of sleeps, all inside one POST. Vercel default function timeouts (10-60s) will kill large searches mid-scrape. The field list includes Contact Data and Atmosphere fields, Google's most expensive Details SKUs (~$0.02+/call), and there is no caching by `place_id`, so repeated searches re-bill identical lookups.

**Fix:** Bounded-concurrency fetching (`Promise.all` over chunks of 5-10), an explicit `maxDuration` on the route, an LRU or Firestore cache keyed on `place_id`, and trim the field list to what the UI renders. For >20 results, move to an async job model with client polling.

### H8. No quota/rate-limit handling or retry in the Places client **[UNVERIFIED]**
**`src/services/googlePlaces.ts`**

All non-OK statuses are handled identically (`console.error` + `break`). No backoff on `OVER_QUERY_LIMIT`, no distinct handling of `REQUEST_DENIED`, no retry when a `next_page_token` request returns `INVALID_REQUEST` (Google page tokens are frequently not valid immediately; the fixed 2000ms sleep is not guaranteed sufficient). `response.ok` is never checked before `response.json()`, so an HTML error body throws and is swallowed.

**Fix:** Retry pagetoken requests 2-3 times with increasing delay on `INVALID_REQUEST`; exponential backoff on `OVER_QUERY_LIMIT`; throw on `REQUEST_DENIED`. Check `response.ok` before parsing.

### H9. `keyword` and `location` accepted with no type or length validation **[UNVERIFIED]**
**`src/app/api/search/route.ts`**

Only truthiness is checked. A non-string body value (object, array, number) passes and flows into `URLSearchParams` and the interpolation `` `${query} in ${location}` `` (`googlePlaces.ts:149`), producing `"[object Object] in [object Object]"` queries that still trigger billable API calls and `MIN_CHARGE` deduction. Megabyte-long strings are also accepted, forwarded to Google, and stored verbatim in Firestore history. (No URL injection: `URLSearchParams` encodes correctly.)

**Fix:** A small zod schema for `SearchRequest` covering `keyword` (≤100 chars), `location` (≤120 chars), `radius`, and `max_results`; trim, reject empty-after-trim and control characters, return 400 otherwise.

### H10. Deploy configuration is internally contradictory and does not parse **[UNVERIFIED]**
**`nginx.conf:23` and `frontend/package.json`**

Three mutually exclusive deployment stories coexist: `vercel.json` (Vercel + `/__/auth` rewrite), `nginx.conf` (self-hosted, `proxy_pass http://localhost:3000`, i.e. `next start`), and a comment at `next.config.ts:13` claiming headers live "in firebase.json", which does not exist. The nginx proxy is impossible with the current config since `next start` refuses to run under `output: 'export'`. Separately, `nginx.conf:23` reads `root /frontend` with no terminating semicolon, so the file does not parse at all; it also carries placeholders (`your-domain.com` at :3,:11; `/path/to/your/certificate.crt` at :14; `/path/to/your/app/out` at :59). And `package.json`'s `export` script runs `next export`, which was removed in Next 14+ and aborts immediately on 15.3.1.

**Fix:** Pick one target. If Vercel: delete `nginx.conf`, keep `vercel.json`, drop `output: 'export'`. If nginx: delete `vercel.json`, drop `output: 'export'`, run `next start`. Either way, add the semicolon or rename the file to `nginx.conf.example`, delete the stale firebase.json comment, and delete the `export` script.

### H11. Pricing config duplicated in three places while the canonical module is dead **[UNVERIFIED]**
**`src/lib/pricing.ts`, `src/app/api/search/route.ts:40`, `src/app/dashboard/search/Search.tsx:17`**

`lib/pricing.ts` defines `PRICING_CONFIG` plus `calculateSearchCost`/`calculateActualCost` and is imported by nothing. Real pricing lives in two independent copies (the Search.tsx one is even commented "should match backend"). `INITIAL_TOKENS` is separately hardcoded as literal `200` three times in `adminTokenService.ts`. Two sources of truth for money math means a price change silently fails to apply server-side, and the client can display a cost different from what is charged.

**Fix:** Make `lib/pricing.ts` the single source; import it in both the route and `Search.tsx`, and replace the `200` literals.

### H12. `Business` type duplicated with divergent photo field; photos can never render **[UNVERIFIED]**
**`src/app/dashboard/leads/Table.tsx:48,97`; `src/app/dashboard/leads/[id]/page.tsx:164,245`; `src/app/dashboard/page.jsx:80`; `src/services/googlePlaces.ts:67`**

`Table.tsx` declares its own `Business` with `photo_reference`; `lib/types.ts` declares `Business` with `image_url`. The service maps `photos[0].photo_reference` into `image_url`, so persisted docs have `image_url` only, while all three UI surfaces read `business.photo_reference`, which is always `undefined`. Business photos therefore never render. The value stored is a raw photo reference token, not a URL, so the field name is misleading either way.

**Fix:** Delete the local type in `Table.tsx`, import from `lib/types`, standardize on one field name end to end (`photo_reference` is the accurate one), and have `api/search/route.ts` import `SearchRequest`/`SearchResponse` from `lib/types` instead of redeclaring them.

### H13. Dashboard shows infinite "Loading..." for signed-out users **[UNVERIFIED]**
**`src/app/dashboard/page.jsx`**

`fetchLatestQuery` early-returns when `!user?.uid` without calling `setLoading(false)`. `loading` starts `true` and the render short-circuits on `if (loading)` before any auth check, so the page never leaves the spinner with no user.

**Fix:** Consume `loading` from `useAuth()`, render an auth gate, and call `setLoading(false)` once auth resolves with no user.

### H14. Lint fails with real errors but is silenced **[UNVERIFIED, empirically reproduced per source finding]**
**`next.config.ts` (`eslint.ignoreDuringBuilds: true`)**

`pnpm lint` exits 1 with genuine errors (unused vars in `SearchForm.tsx`, ten `@typescript-eslint/no-explicit-any` errors across `init-middleware.ts`, `types.ts`, `googlePlaces.ts`), but builds print "Skipping linting" so nothing gates. The `lint` script also uses `next lint`, deprecated in 15.x and removed in Next 16.

**Fix:** Change the script to `eslint src`, fix the ~11 errors, then remove `eslint.ignoreDuringBuilds`.

## 4. Medium

### M1. Unauthenticated admin test endpoint reachable in production **[VERIFIED]**
**`src/app/api/test-admin/route.ts:5`**
*(Downgraded from critical.)*

`GET /api/test-admin` has no auth check, no `NODE_ENV` guard, and nothing gating it externally. It calls `adminAuth.listUsers(1)` and reads a Firestore doc with the privileged Admin SDK, then returns success plus `userCount`; on failure it returns the raw error object.

**Why not critical:** `listUsers(1)` caps at one user, so `userCount` is only 0 or 1 (no meaningful count, no PII). And JSON-serializing errors does not leak stack traces: plain `Error` serializes to `{}` (message/stack are non-enumerable) and `FirebaseError.toJSON()` returns only `{code, message}`. Net effect is unauthenticated reconnaissance confirming the service account is live, plus limited error-code disclosure. No writes, no escalation path.

**Fix:** Delete the route. If you need a health check, return `{ok: true}` only, never call `listUsers`, never return the raw error, and gate it behind an admin claim or secret header.

## 6. Checked and Dismissed

- **"Hardcoded Google Maps API key enables billing abuse" — rejected as critical, retained as M2.** The literal key is genuinely in source, in the built bundle, and in git history, but it is **dead**: direct requests to Google's Geocoding and Places Photo APIs return `403 REQUEST_DENIED` / "The provided API key is invalid", with and without a `Referer` header (referrer restrictions produce a distinct error, so that is ruled out). No billing or quota impact is possible with a revoked key. What survives is credential hygiene plus a real broken-images bug on the dashboard, both at medium.
- **"`/api/tokens/add` is unauthenticated" — corrected.** `verifyIdToken` genuinely runs and rejects forged or expired tokens. The defect is missing authorization, not missing authentication. Because self-signup is open Google OAuth, this does not reduce exploitability; it only means the attacker leaves a real UID behind.
- **`AdminTokenService` / `adminAuth` / `adminDb` naming — not an authorization gate.** These refer to the Firebase Admin SDK (privileged server-side DB access), not admin-only access control. Nothing in that naming restricts any endpoint to privileged users.
- **URL injection via `keyword`/`location` — not present.** `URLSearchParams` encodes values correctly. The problem in H9 is type/length validation and billable-behavior control, not injection.
- **`deductTokens` atomicity — correct as written.** The Firestore transaction properly rejects on insufficient balance and cannot produce a negative balance. The bugs (H6, M20) are in the check-then-act pattern *around* it, not in it.
